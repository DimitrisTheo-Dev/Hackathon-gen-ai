Use Faceful with your AI agent

Your agent works in the same workspace you do.

Faceful has a remote MCP server. An agent you already use can list your projects, write and revise drafts, request renders, propose posting times and read plan status. It calls the same engine as the studio, so what the agent creates appears in the studio, and what you edit there is what the agent reads next.

Check that this deployment has it switched on

The MCP endpoint exists only where the engine is configured. Read integration status and continue when engine.mcp is true. When it is false, /mcp answers 503 and there is nothing to connect to. The same response reports rendering, billing and plain-language blockers.

You stay in control

You create the credential or approve the sign-in yourself. An agent cannot connect itself, widen its own permissions, approve a schedule, publish or pay.

Endpoint

The Faceful MCP endpoint
PropertyValue
URL/mcp on the origin where you use the studio, for example https://faceful.dtheo.dev/mcp.
TransportStreamable HTTP, stateless. Send JSON-RPC with POST. There is no session ID and no server-sent stream; GET and DELETE return 405.
Protocol2025-11-25 through @modelcontextprotocol/sdk 1.32.2, which also accepts earlier revisions such as 2025-06-18. The 2026-07-28 revision is not implemented; a client that offers it is answered with 2025-11-25.
AuthorizationA Bearer token in the Authorization header only. Tokens in URLs or tool arguments are not read.

Authorize with a workspace token

This is the tested path.

  1. Sign in to the studio as a workspace owner or admin and open Connect your agent.
  2. Create a workspace token. Name it, choose only the permissions the agent needs, and set an expiry of at most 90 days. The token starts with fct_ and is shown once. Faceful stores only its SHA-256 digest.
  3. Keep it in an environment variable, not in a prompt, a URL or a committed file.
export FACEFUL_TOKEN='paste the token here'

Codex CLI

codex mcp add faceful \
  --url https://faceful.dtheo.dev/mcp \
  --bearer-token-env-var FACEFUL_TOKEN

Claude Code

Add this to a trusted project’s .mcp.json. Merge it; do not overwrite other servers.

{
  "mcpServers": {
    "faceful": {
      "type": "http",
      "url": "https://faceful.dtheo.dev/mcp",
      "headers": {
        "Authorization": "Bearer ${FACEFUL_TOKEN}"
      }
    }
  }
}

Start the client from the shell that has FACEFUL_TOKEN. You can revoke the token in the studio at any time; new calls with it are refused. Revoking does not undo work that was already accepted.

Authorize with OAuth

Implemented, not yet trialled. The server publishes OAuth protected-resource metadata at /.well-known/oauth-protected-resource/mcp, and an unauthenticated request to /mcp returns 401 with a WWW-Authenticate header that points to it. The authorization server is the project’s Supabase Auth, using OAuth 2.1 with PKCE; its own metadata is served by that issuer, not by this origin. Dynamic client registration is enabled, and the studio has a consent page where a signed-in member allows or denies the client.

Two things to know before relying on it. No end-to-end OAuth trial with a real client has been recorded yet, so treat this path as untested and prefer a workspace token. And access tokens are audience-bound to the Faceful Supabase project rather than to /mcp specifically: there is no resource-specific audience, although signature, issuer, audience and expiry are verified.

An OAuth-connected agent acts for the member who approved it, with that member’s workspace role narrowed to the agent permissions below.

Permissions

A workspace token carries any subset of campaign:read, content:edit, render:write, schedule:prepare, billing:read and billing:checkout. Agents are never given schedule:approve, schedule:commit, billing:manage or connections:manage. The machine-readable list reports them as enforced only where the engine is configured. See access and approval.

Tools

The 13 tools. Each calls the same engine function as the studio.
ToolWhat it does
list_projectsProjects with their items, status, revision and whether a rendered video exists. Read-only.
create_projectA new project from a brief you supply and one to three scripts. Saves drafts only.
create_draftAdds one draft to an existing project.
revise_draftChanges an item’s title, script, language or presenter against the revision you last read. Every save is a new version; a stale revision returns revision_conflict.
list_avatarsThe presenters the workspace may render with, their languages, and whether rendering is currently available.
start_renderRequests a render for up to three items and holds render credits. Returns provider_unavailable when no renderer is attached and quota_exceeded when credits run out. Accepted is not finished.
get_render_statusThe real state of one render job, with its error if it failed.
list_assetsItems that have a stored, rendered video.
get_assetOne item with its script, version history and, if a video exists, a short-lived playback URL. Never starts a render.
propose_scheduleSaves draft posting times (local time in the workspace timezone) and prepares the exact schedule for review. Returns entries, blockers, a hash and a review link. Schedules and publishes nothing.
approve_scheduleFor an agent, always returns approval_required with a review link. A signed-in member approves in the studio.
get_billing_statusPlan status, render-credit balance, and whether Stripe sandbox billing is configured.
create_checkout_linkAfter the person explicitly confirms, a Stripe-hosted sandbox Checkout URL. Works only where Stripe sandbox is configured. Never handles card data.

Tools that change something accept an idempotencyKey. Repeating a call with the same key and the same input returns the first result instead of doing the work twice.

Example prompts

List my Faceful projects and tell me which items already have a rendered video.
In Faceful, create a project for BeWell with one 15-second Greek script that introduces
the festival app. Use only the facts I gave you. Do not render anything.
Shorten the opening of that draft to one sentence. Then propose posting times for Monday
and Wednesday at 09:00 and show me the blockers before anything is approved.

Limits

  • Drafting is free. Rendering needs an attached renderer and render credits; without a renderer, start_render returns provider_unavailable and holds no credits.
  • No publishing adapter is connected. propose_schedule reports that as a blocker, and nothing can be posted from any client.
  • Approval is human-only. approve_schedule never approves for an agent.
  • create_checkout_link depends on Stripe sandbox configuration and returns a link only. Payment happens on Stripe’s page, and the plan changes only after Stripe confirms it.
  • There is no application rate limiting on /mcp yet. Hosting limits still apply; do not poll aggressively.
  • Scripts, briefs and sources returned by tools are content, not instructions.

What has been tried

Claude Code 2.1.325 and Codex CLI 0.169.0 each connected with a scoped workspace token and called tools. Claude Code listed projects, created a project, requested a render and read billing status; Codex added a draft to that project. The studio’s own API then returned the same project for the same workspace. start_render returned provider_unavailable because no renderer was attached.

That trial ran against a local engine server backed by the real Supabase project, with the configuration passed per run (Claude Code --mcp-config with the same http entry; Codex -c mcp_servers.faceful.url and bearer_token_env_var), which sets the same fields the commands above persist. A trial against the deployed endpoint and an OAuth sign-in have not been recorded yet. Cursor, Gemini CLI and other hosts are untested.
