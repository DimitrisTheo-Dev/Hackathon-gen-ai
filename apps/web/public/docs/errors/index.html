Errors and recovery

Keep the work. Resolve the specific blocker.

A failed connection must not turn into fixture success. A failed destination must not erase successful posts. Recover from the recorded state and preserve the operation ID.

  • Live One error shape for the studio and agents

One error shape for the studio and for agents

The domain API under /v1 returns the codes below as { error: { code, message, retryAfterSeconds, reviewUrl } }, and MCP tools return the same fields in a result marked isError. A deployment without engine credentials answers 503. The separate public discovery API returns RFC 9457 JSON errors for unsupported routes and methods.

Codes and what to do

HTTP 401unauthenticated
Sign in or supply a valid scoped connection token. Never substitute a provider secret.
HTTP 403forbidden
Check workspace membership and scope. Ask the owner for the specific authority needed.
HTTP 404not_found
The object does not exist in this workspace. Objects in another workspace are reported the same way.
HTTP 409revision_conflict
Read the latest item, compare changes, then retry with its current revision. Preserve unsaved input.
HTTP 403approval_required
Open the exact review URL returned by the backend. A model assurance cannot replace approval. Over MCP, approve_schedule returns this as a normal result: it is the designed boundary, not a failure.
HTTP 409stale_manifest
Prepare and review a new immutable schedule manifest for the edited content.
HTTP 409idempotency_conflict
Do not reuse an operation key with different input. Reconcile the earlier request first.
HTTP 429quota_exceeded
Inspect remaining render credits and renders in progress. Retrying does not reset limits; a held credit comes back only when its job fails or is cancelled.
HTTP 422unsupported
Read current capabilities and choose a supported format/channel combination.
HTTP 503provider_unavailable
On a render, no renderer is attached: nothing was started and no credits were held. Otherwise read the message and retry only when the named service is available.
HTTP 400validation_error
Correct the reported field. For an expired schedule, choose future times and obtain fresh authorization. Never silently publish now.
HTTP 502unknown_outcome
Poll/reconcile with the provider correlation ID. Do not create a duplicate post.

When requests are throttled

Honor the returned retry hint or Retry-After; avoid concurrent retry loops. There is no application rate limiting on /v1 or /mcp yet; hosting limits still apply.

When a request times out

Read the existing operation by its stable ID or repeat the original request with the same operation key and identical payload. A side-effecting retry must return the existing operation, not start a second render or post. A timeout is not proof that nothing happened.

When only one channel fails

Inspect each target separately. Keep provider-accepted and published destinations intact. Reconnect or edit the failed target as required, and retry only when the backend marks that job eligible. A changed provider-accepted post needs a new version and explicit cancellation/rescheduling when supported.

When preview media expires

Refresh the authorized media reference. Do not replace the current revision with an older asset, expose a private storage bucket, or show a completed state without playable media.

Useful details to retain

Keep the campaign/item ID, revision, operation/job ID, timestamp, error code, the X-Correlation-Id response header and any provider correlation ID. Keep tokens, private payloads, cookies, and signing URLs out of diagnostic logs and support messages.
